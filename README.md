**RF4 (invitar responsables): implementado y validado de punta a punta en Windows.** Un administrador invita a un responsable de eslabón desde `/dashboard/eslabones/[id]/invitar` (link "Invitar responsable" junto a cada eslabón). La invitación **no se persiste en una tabla propia**: se codifica como un JWT firmado (`src/infra/auth/invitacion.ts`, librería `jose`, ya usada indirectamente por Auth.js) con el email, el eslabón y el tenant, válido 7 días — decisión tomada porque este entorno no puede correr `prisma migrate dev` (bloqueo de red ya documentado), así que una tabla `Invitacion` nueva hubiese quedado sin poder aplicarse hasta la próxima sesión en Windows; con un token stateless no hace falta migración. Quien recibe el correo (enviado con [Resend](https://resend.com), `src/infra/email/resend.ts`) entra a `/invitacion/aceptar?token=...`, elige nombre y contraseña, y ahí recién se crea el `Usuario` (`rol: RESPONSABLE`, `eslabonId` fijo del token) — nunca hay una fila con contraseña vacía. Trade-off aceptado y documentado: el administrador no puede ver ni revocar invitaciones ya enviadas antes de que se acepten (no hay fila que listar); se puede agregar una tabla de auditoría más adelante sin romper el mecanismo. 4 pruebas unitarias del token (firma, alteración, secreto distinto) en `src/infra/auth/__tests__/invitacion.test.ts`. **Requiere `RESEND_API_KEY` en `.env`** (ver `.env.example`) — sin un dominio propio verificado en Resend, el modo sandbox solo permite enviar a la dirección con la que se creó la cuenta de Resend, suficiente para probar el flujo ahora. Probado en Windows: invitación enviada desde `/dashboard/eslabones/[id]/invitar` → correo recibido con el eslabón/empresa correctos → cuenta de responsable creada en `/invitacion/aceptar` → login exitoso con esa cuenta.

**RF5-RF7 (ciclos de pulso reales): implementado y validado de punta a punta en Windows.** Un administrador abre un ciclo de pulso desde `/dashboard/ciclos` (`src/infra/ciclos/abrirCiclo.ts`) — solo puede haber un ciclo `ABIERTO` por empresa a la vez — y se notifica por correo (Resend) a los responsables elegibles: los que tienen un eslabón asignado que participa de al menos una conexión `completa`. Cada responsable completa el cuestionario en `/dashboard/ciclos/[id]/responder` (escala Likert 1-5, con "no sé"/"no aplica") para las conexiones de su eslabón — una respuesta por conexión por ciclo por responsable, según el `@@unique` ya existente en el schema (`src/infra/ciclos/registrarRespuestas.ts`). Al cerrar el ciclo (`src/infra/ciclos/cerrarCiclo.ts`, botón de administrador), por cada conexión completa se calcula salud/criticidad/riesgo con el motor v1 ya probado, se persiste `ResultadoConexion` como snapshot inmutable (nunca una referencia viva a `Conexion` — RNF6), se calcula el conjunto no dominado de eslabones más débiles y el índice de integración (RF16), y se persiste `ResultadoCiclo`. Una conexión sin ninguna respuesta válida en el ciclo no genera resultado — es ausencia de dato, no un cero — y así nace la cobertura parcial de RF10 (`src/infra/ciclos/cobertura.ts`). `RespuestaCruda`/`ResultadoConexion`/`ResultadoCiclo` no tienen `empresaId` propio, así que se acceden con una transacción manual + `set_config`, mismo patrón que `aceptarInvitacion.ts`. `/dashboard/ciclos/[id]` muestra los resultados (índice de integración, eslabón(es) más débil(es), salud/riesgo/dependencia por conexión, cobertura) — primer corte de RF9, no el panel completo. Requirió que un `RESPONSABLE` conozca su propio `eslabonId` en la sesión: se agregó a los tipos de Auth.js y a `login_lookup()` en Postgres (`prisma/auth_functions.sql`). **Bug real encontrado al aplicar ese SQL en Neon:** `CREATE OR REPLACE FUNCTION` no puede cambiar el tipo de retorno de una función existente (agregar una columna a `RETURNS TABLE` cuenta como cambio de tipo, error `42P13`) — corregido agregando `DROP FUNCTION IF EXISTS` antes del `CREATE` (commit `236f3c8`). Probado en Windows con datos reales: se abrió un ciclo (correo recibido correctamente), el responsable de "Compras" respondió el cuestionario (una sola conexión, como corresponde: solo ese eslabón tenía responsable), y al cerrar el ciclo la pantalla de resultados mostró salud 75, riesgo 42, índice de integración 90, cobertura 100% y la conexión marcada como único "eslabón más débil" — coherente con los datos declarados y la única respuesta cargada.

**Recuperación de contraseña: implementado y validado de punta a punta en Windows.** Faltaba pese a estar asumido por ADR-0003 junto a RF1/RF4. Desde `/login` ("¿Olvidaste tu contraseña?") se llega a `/recuperar-contrasena`, se pide el email, y si existe una cuenta con ese email se manda un correo (Resend) con un enlace de un solo uso a `/recuperar-contrasena/confirmar?token=...`, donde se elige una contraseña nueva. Mismo criterio que la invitación de RF4 (`src/infra/auth/recuperacion.ts`): token JWT firmado, sin tabla nueva — pero con una diferencia importante: el token tiene que dejar de servir después de un solo uso. Se logra sin persistir nada, con una huella (hash corto) del `passwordHash` vigente al emitir el token, incluida en el propio JWT; al confirmar, se recalcula esa huella contra el `passwordHash` actual — si no coincide (la contraseña ya cambió, con este enlace o cualquier otro medio), se trata como vencido. Vigencia de 1 hora (más corta que los 7 días de una invitación, por ser un flujo más sensible). Reutiliza `login_lookup()`/`buscarUsuarioPorEmail()` ya existente, sin SQL nuevo — no hace falta ninguna migración para esta función. Sin enumeración de cuentas (mismo criterio que el login): la respuesta de `POST /api/recuperar-contrasena` es idéntica exista o no el email, y aunque falle el envío del correo. Sin limitación de tasa propia todavía (documentado en el código): el peor abuso posible es mandar correos de más a una bandeja ajena, no un riesgo de cuenta — se puede sumar después sin romper el mecanismo. `tsc`/`eslint`/`vitest` limpios (**49/49 tests**, 4 nuevos que prueban las propiedades criptográficas del token —firma, huella, vencimiento— sin tocar la base; la verificación completa contra un usuario real queda para una prueba de integración futura, junto con el resto de flujos críticos de autenticación). De paso, se corrigió un test intermitente encontrado en `invitacion.test.ts` ("firma alterada" mutaba el último carácter de un JWT HS256, que en base64url puede tener bits de relleno sin significado real) — mismo fix aplicado al test nuevo. Probado en Windows de punta a punta: se recargó `RESEND_API_KEY` con una clave nueva de Resend de permiso mínimo ("Sending access", reemplazando la anterior de "Full access" que se revocó) y `RESEND_FROM_EMAIL=onboarding@resend.dev` (modo sandbox, sin dominio propio verificado). Desde `/login` se pidió la recuperación para una cuenta existente, llegó el correo real vía Resend con el enlace de un solo uso, se eligió una contraseña nueva en `/recuperar-contrasena/confirmar`, redirigió a `/login`, y el login con la contraseña nueva entró correctamente a `/dashboard` — el flujo completo queda validado de punta a punta.

**Pruebas automatizadas ampliadas a flujos críticos de mutación: implementado y validado de punta a punta en Windows.** Hasta ahora la única prueba de integración era la de RNF1 (aislamiento multi-tenant); el resto de la lógica de negocio de las mutaciones (qué reglas se cumplen, qué errores se lanzan) no tenía cobertura automatizada propia, más allá de la validación manual en Windows ya documentada en cada sección de este README. Dos archivos nuevos: `src/infra/auth/__tests__/mfa.test.ts` (unitario, sin base de datos — corre en `npm run test`, cubre `generarSecretoMfa`/`construirOtpauthUrl`/`verificarCodigoMfa`: código válido aceptado, código de otro secreto o vencido rechazado) y `src/infra/__tests__/flujosMutacion.integration.test.ts` (mismo criterio que RNF1: necesita `DATABASE_URL` real, corre con `npm run test:integration` en Windows). Este último cubre: registro de cuenta (`registrarEmpresaYAdmin` crea empresa+administrador atómicamente; un email duplicado lanza `EmailYaRegistradoError` sin dejar una empresa huérfana — la transacción realmente hace rollback completo); activación de MFA (un código TOTP válido calculado a partir del secreto persistido activa `mfaHabilitado`, uno inválido no); CRUD de eslabones/conexiones (una conexión sin los 5 datos de criticidad queda `completa: false`, completarlos la marca `completa: true`, declarar la misma conexión dos veces viola la restricción única `P2002`); y el ciclo de pulso completo abrir → responder → cerrar (RF5-RF7): no se puede abrir un segundo ciclo mientras el primero sigue `ABIERTO`, responder por una conexión no asignada al eslabón del responsable lanza `ConexionNoAsignadaError`, la métrica de duración de RNF9 se persiste junto con la respuesta, cerrar el ciclo persiste `ResultadoConexion`/`ResultadoCiclo` correctamente, y tanto cerrar un ciclo ya cerrado como responder en uno ya cerrado lanzan `CicloNoAbiertoError` (dos clases de error con el mismo nombre pero definidas en archivos distintos — `cerrarCiclo.ts` y `registrarRespuestas.ts` — importadas con alias en la prueba para no confundirlas). `tsc`/`eslint`/`npm run test` limpios en Mac (**56/56 tests**, sin red: los 7 nuevos son los de `mfa.test.ts`; los de `flujosMutacion.integration.test.ts` no corren ahí a propósito, mismo motivo que RNF1). **Confirmado en Windows contra Neon real: `npm run test:integration` pasa 24/24.** En el camino aparecieron y se corrigieron dos problemas propios de la prueba (no del código de producción): un falso negativo por RLS "falla cerrado" (una consulta de verificación sin `tenantClient()` siempre devolvía `[]`, aunque el rollback atómico real funcionaba bien) y contención de conexiones contra Neon al correr los dos archivos de integración en paralelo (se agregó `fileParallelism: false` en `vitest.integration.config.ts`, más un `beforeAll` que "despierta" la base con una consulta trivial antes del primer test del run, igual criterio que ya usaba RNF1).

**Bug conocido del botón "Cerrar sesión": revisado, no se reprodujo — validado de punta a punta en Windows.** Quedaba pendiente de revisar sin ningún síntoma documentado más allá de la nota en "Próximo paso" (sin ADR, TODO ni comentario en el código). ## Cómo levantar el proyecto

```bash
git clone https://github.com/alexhsantamaria/ChainPulse.git
cd ChainPulse
npm install
npm run prisma:generate
npm run typecheck         # tsc --noEmit
npm run lint               # eslint .
npm run test               # vitest run — 49 pruebas (motor v1 + infra), sin red
npm run test:integration    # vitest run --config vitest.integration.config.ts — RNF1, necesita DATABASE_URL real
npm run dev                 # Next.js en http://localhost:3000
```

`prisma/schema.prisma` usa una base PostgreSQL real en Neon (`DATABASE_URL` en `.env`, no versionado). Para migraciones nuevas, cambiar temporalmente `DATABASE_URL` al rol `neondb_owner` (dueño de las tablas); para desarrollo normal, usar el rol restringido `chainpulse_app` (sujeto a las políticas RLS de `prisma/rls.sql`, ya aplicadas en la base). `npm run test:integration` crea y borra sus propios dos tenants de prueba en cada corrida (nunca toca las cuentas de prueba existentes) para verificar RLS con datos reales — ver el `## Estado` de RNF1 más abajo.
