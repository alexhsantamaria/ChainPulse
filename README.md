# ChainPulse

Producto SaaS multi-empresa que detecta dónde existe descoordinación entre áreas, procesos, personas y sistemas de una organización, identifica el eslabón más débil del flujo y recomienda qué mejorar primero, con seguimiento de avance en el tiempo.

**Autenticación (RF1/RF4): implementada y validada de punta a punta.** Auth.js v5 (Credentials) con hash Argon2id, MFA (TOTP) verificable para `ADMINISTRADOR`, rate limiting con bloqueo temporal y sin enumeración de usuarios — según ADR-0003. `email` es único global (no compuesto con `empresaId`); el login resuelve el tenant vía la función Postgres `login_lookup()` (`prisma/auth_functions.sql`, `SECURITY DEFINER`, única excepción acotada al aislamiento RLS — ver addendum de ADR-0003). Probado en Windows contra Neon: `npm run prisma:seed` crea el usuario de prueba, el login en `/login` autentica y `/api/auth/session` devuelve el JWT con `empresaId`/`rol` correctos.

**RF1 (registro de cuenta) y activación de MFA: implementados y validados de punta a punta.** `/registro` crea la empresa y el administrador en una transacción atómica (`src/infra/auth/registro.ts`) e inicia sesión automáticamente con las mismas credenciales; `/activar-mfa` muestra el código QR (motor ya existente en `src/infra/auth/mfa.ts`) y exige confirmar un código antes de dejar la cuenta operativa, según manda ADR-0003 para `ADMINISTRADOR`. Probado en Windows: registro → sesión automática → escaneo del QR con una app real (Google Authenticator) → código aceptado → `mfaHabilitado` activo. Ver addendum de ADR-0003 para el detalle de cómo se resolvió crear un tenant nuevo bajo RLS (más simple de lo previsto: no hizo falta una función `SECURITY DEFINER`). `src/middleware.ts` protege `/activar-mfa` y `/dashboard/*` (todavía sin construir, pero ya queda cubierto en el matcher) redirigiendo a `/login` sin sesión — corre en el Edge runtime de Next.js sobre la sesión JWT, sin tocar la base de datos. Corregido un bug real detectado al probarlo en Windows: el middleware no puede importar Argon2/Prisma en el Edge runtime, así que la configuración de Auth.js se separó en `src/auth.config.ts` (sin el proveedor `Credentials`, la usa el middleware) y `src/auth.ts` (completo, para las rutas de API) — ver addendum de ADR-0003. Validado en Windows: sin sesión, `/activar-mfa` redirige a `/login`.

**RF4 (invitar responsables): implementado y validado de punta a punta en Windows.** Un administrador invita a un responsable de eslabón desde `/dashboard/eslabones/[id]/invitar` (link "Invitar responsable" junto a cada eslabón). La invitación **no se persiste en una tabla propia**: se codifica como un JWT firmado (`src/infra/auth/invitacion.ts`, librería `jose`, ya usada indirectamente por Auth.js) con el email, el eslabón y el tenant, válido 7 días — decisión tomada porque este entorno no puede correr `prisma migrate dev` (bloqueo de red ya documentado), así que una tabla `Invitacion` nueva hubiese quedado sin poder aplicarse hasta la próxima sesión en Windows; con un token stateless no hace falta migración. Quien recibe el correo (enviado con [Resend](https://resend.com), `src/infra/email/resend.ts`) entra a `/invitacion/aceptar?token=...`, elige nombre y contraseña, y ahí recién se crea el `Usuario` (`rol: RESPONSABLE`, `eslabonId` fijo del token) — nunca hay una fila con contraseña vacía. Trade-off aceptado y documentado: el administrador no puede ver ni revocar invitaciones ya enviadas antes de que se acepten (no hay fila que listar); se puede agregar una tabla de auditoría más adelante sin romper el mecanismo. 4 pruebas unitarias del token (firma, alteración, secreto distinto) en `src/infra/auth/__tests__/invitacion.test.ts`. **Requiere `RESEND_API_KEY` en `.env`** (ver `.env.example`) — sin un dominio propio verificado en Resend, el modo sandbox solo permite enviar a la dirección con la que se creó la cuenta de Resend, suficiente para probar el flujo ahora. Probado en Windows: invitación enviada desde `/dashboard/eslabones/[id]/invitar` → correo recibido con el eslabón/empresa correctos → cuenta de responsable creada en `/invitacion/aceptar` → login exitoso con esa cuenta.

**Prisma sin motor Rust (Windows ARM64):** Prisma no publica un motor de consultas nativo para Windows ARM64 (`query_engine-windows.dll.node is not a valid Win32 application` al correr `npm run prisma:seed`; issue de Prisma cerrado como "not planned"). Se cambió a `engineType = "client"` en `prisma/schema.prisma` (modo GA "sin motor Rust" desde Prisma 6.16) con `@prisma/adapter-pg` como driver adapter — ver addendum de ADR-0003. No afecta a `prisma generate`/`prisma migrate dev` (usan el `schema-engine`, un proceso separado que sí corre bien vía emulación); solo cambia cómo el cliente en runtime (`src/infra/prisma/client.ts`, `prisma/seed.ts`) se conecta a Postgres.

**RF2/RF3 (declarar la cadena): implementados y validados de punta a punta en Windows.** Un administrador logueado declara los eslabones de su cadena en `/dashboard/eslabones` y las conexiones (dependencias) entre ellos en `/dashboard/conexiones` — grafo dirigido con `origenId`/`destinoId` únicos por par (`Conexion.@@unique([origenId, destinoId])`). Al declarar una conexión, los 5 datos de RF3 (grado de dependencia, impacto sobre la promesa al cliente, si existe alternativa, tiempo tolerable, tiempo de recuperación) se piden agrupados en un solo formulario, pero son opcionales al guardar: una conexión sin los 5 confirmados queda marcada `completa: false` (`src/infra/conexiones/completitud.ts`, con pruebas unitarias propias) y se puede completar después desde `/dashboard/conexiones/[id]/editar` (`PATCH /api/conexiones/[id]`) — igual que exige el criterio de aceptación de RF3. Todas las rutas nuevas pasan por `tenantClient()` (RLS + filtro de tenant) y están protegidas por el middleware (`/dashboard/:path*`). Probado en Windows: 4 eslabones y 3 conexiones declaradas contra Neon, todas quedaron `completa: true` con los 5 datos confirmados.

**RF5-RF7 (ciclos de pulso reales): implementado y validado de punta a punta en Windows.** Un administrador abre un ciclo de pulso desde `/dashboard/ciclos` (`src/infra/ciclos/abrirCiclo.ts`) — solo puede haber un ciclo `ABIERTO` por empresa a la vez — y se notifica por correo (Resend) a los responsables elegibles: los que tienen un eslabón asignado que participa de al menos una conexión `completa`. Cada responsable completa el cuestionario en `/dashboard/ciclos/[id]/responder` (escala Likert 1-5, con "no sé"/"no aplica") para las conexiones de su eslabón — una respuesta por conexión por ciclo por responsable, según el `@@unique` ya existente en el schema (`src/infra/ciclos/registrarRespuestas.ts`). Al cerrar el ciclo (`src/infra/ciclos/cerrarCiclo.ts`, botón de administrador), por cada conexión completa se calcula salud/criticidad/riesgo con el motor v1 ya probado, se persiste `ResultadoConexion` como snapshot inmutable (nunca una referencia viva a `Conexion` — RNF6), se calcula el conjunto no dominado de eslabones más débiles y el índice de integración (RF16), y se persiste `ResultadoCiclo`. Una conexión sin ninguna respuesta válida en el ciclo no genera resultado — es ausencia de dato, no un cero — y así nace la cobertura parcial de RF10 (`src/infra/ciclos/cobertura.ts`). `RespuestaCruda`/`ResultadoConexion`/`ResultadoCiclo` no tienen `empresaId` propio, así que se acceden con una transacción manual + `set_config`, mismo patrón que `aceptarInvitacion.ts`. `/dashboard/ciclos/[id]` muestra los resultados (índice de integración, eslabón(es) más débil(es), salud/riesgo/dependencia por conexión, cobertura) — primer corte de RF9, no el panel completo. Requirió que un `RESPONSABLE` conozca su propio `eslabonId` en la sesión: se agregó a los tipos de Auth.js y a `login_lookup()` en Postgres (`prisma/auth_functions.sql`). **Bug real encontrado al aplicar ese SQL en Neon:** `CREATE OR REPLACE FUNCTION` no puede cambiar el tipo de retorno de una función existente (agregar una columna a `RETURNS TABLE` cuenta como cambio de tipo, error `42P13`) — corregido agregando `DROP FUNCTION IF EXISTS` antes del `CREATE` (commit `236f3c8`). Probado en Windows con datos reales: se abrió un ciclo (correo recibido correctamente), el responsable de "Compras" respondió el cuestionario (una sola conexión, como corresponde: solo ese eslabón tenía responsable), y al cerrar el ciclo la pantalla de resultados mostró salud 75, riesgo 42, índice de integración 90, cobertura 100% y la conexión marcada como único "eslabón más débil" — coherente con los datos declarados y la única respuesta cargada.

**RF8 (recomendación priorizada): implementado y validado en Windows.** Cuando se identifica el conjunto de eslabones más débiles de un ciclo (RF7), el sistema genera una recomendación con prioridad (ALTA/MEDIA/BAJA) y un texto de acción concreta para cada una (`src/engine/recomendacion.ts`, función pura, 7 pruebas). RF8 pide reglas según "el tipo de fricción reportada" — un campo que no existe en ningún lado del requisito (sin catálogo, sin campo en el modelo, sin criterio de aceptación) — así que, con Alex, se decidió un v1 simplificado: las reglas usan solo lo que ya se calcula por conexión (salud, grado de dependencia, si tiene alternativa declarada), sin agregar ninguna pregunta al cuestionario ni tocar el schema. La recomendación **no se persiste**: se calcula al leer los resultados (`src/infra/ciclos/resultados.ts`) a partir de los valores ya inmutables de `ResultadoConexion` — trade-off documentado en el propio código (si las reglas cambian más adelante, un ciclo ya cerrado mostraría el texto nuevo, aunque el puntaje numérico no cambia). Se muestra junto a cada eslabón más débil en `/dashboard/ciclos/[id]`. `tsc`/`eslint`/`vitest` limpios (41/41 tests). Probado en Windows reabriendo el ciclo ya cerrado de la prueba de RF5-RF7 (sin necesidad de abrir uno nuevo, porque no persiste nada): con salud 75, dependencia ALTA y sin alternativa declarada, mostró correctamente prioridad **media** y el texto sugiriendo definir un respaldo — coincide exactamente con la regla esperada.

**RF9 (panel completo de resultados): implementado y validado en Windows.** Faltaban dos cosas del panel completo que pide RF9: el cuarto valor por conexión (criticidad) y el histórico/tendencia entre ciclos. La criticidad tampoco se persiste como columna propia — `ResultadoConexion.criticidadSnapshot` ya guarda el `DatosCriticidad` completo (RNF6), así que se recalcula al leer con `calcularCriticidad()`, mismo criterio ya aceptado para la recomendación de RF8. `/dashboard/ciclos/[id]` ahora muestra los 4 valores (salud, criticidad, riesgo, dependencia) y, cuando hay más de un ciclo cerrado, la tendencia de salud de esa conexión ("Tendencia de salud: 60 → 68 → 75"). `/dashboard/ciclos` ahora muestra el índice de integración de cada ciclo cerrado y, arriba de la lista, la tendencia del índice entre ciclos cuando hay más de uno cerrado. RF10 (cobertura de respuesta explícita) ya estaba satisfecho desde RF5-RF7, sin cambios ahí. `tsc`/`eslint`/`vitest` limpios (41/41 tests, sin pruebas nuevas: son cambios de lectura/presentación sobre cálculo ya probado). Probado en Windows en tres ciclos sucesivos sobre la misma conexión Compras → Producción: ciclo 1 (RF5-RF7) con salud 75 → criticidad 70, riesgo 42, índice de integración 90; ciclo 2 respondido con "No sé" (sin dato válido, RF10) → no genera `ResultadoConexion`, índice 0; ciclo 3 con salud 25 → riesgo 62, recomendación pasa correctamente a prioridad **alta** (rama del motor de RF8 no probada hasta ahora, salud < 40 siempre es alta), índice 0. La tendencia de salud de la conexión mostró "75 → 25" — saltea el ciclo sin dato en vez de mostrar un 0 falso en el medio, confirmando que "ausencia de dato, no un cero" (RF10) se respeta también en la tendencia. La tendencia del índice de integración en `/dashboard/ciclos` mostró "90 → 0 → 0", matemáticamente correcto: con una sola conexión declarada en todo el dataset de prueba, el índice es binario (0% o 100% de la cadena en salud aceptable) — con más conexiones declaradas se vería más gradual, no es un defecto de la fórmula (ya probada con 4 tests unitarios propios). **Corrección (post-análisis previo a Incremento 2):** ni la tendencia de salud por conexión ni la del índice de integración chequeaban `ruleVersion` — encadenaban valores de cualquier ciclo cerrado sin verificar que compartieran versión del motor. `requirements.md` ya anticipa que las fórmulas se van a recalibrar con datos reales de los pilotos (Sección 12); sin este filtro, ese día la tendencia mostraría un "salto" que en realidad sería solo un cambio de regla. Corregido: ambas tendencias ahora se cortan en la versión vigente, sin mezclar. Sin validación visual en Windows para esto — con una sola versión existiendo hoy (`engine-v1.0.0`) el comportamiento observable no cambia; previene un problema futuro, no corrige uno ya visto. `tsc`/`eslint`/`vitest` limpios (41/41).

**RNF1 (pruebas de integración de aislamiento multi-tenant): implementado y validado en Windows.** `prisma/rls.sql` (RLS de Postgres) estaba escrito y aplicado a mano en Neon desde hace varias sesiones, pero nunca probado de punta a punta con una prueba automatizada — el propio archivo lo marcaba pendiente. `src/infra/prisma/__tests__/aislamientoMultitenant.integration.test.ts` crea dos tenants sintéticos de forma realista (empresa, administrador, 2 eslabones, 1 conexión completa, 1 ciclo cerrado con respuesta y resultados) y prueba las dos capas de RNF1 (ADR-0001, "cinturón y tirantes"): `tenantClient()` a nivel de aplicación, y RLS a nivel de base de datos — incluyendo el caso "el código se olvida del filtro" (consulta sin `where`, id explícito de otro tenant) y el caso "sin ningún tenant fijado" (debe fallar cerrado, no abierto). Cubre también las tres tablas hijas sin `empresaId` propio (`RespuestaCruda`, `ResultadoConexion`, `ResultadoCiclo`), cuyas políticas RLS por subconsulta tampoco se habían ejercitado nunca contra datos reales. Limpia sus propios tenants de prueba al final (`afterAll` + `ON DELETE CASCADE`), nunca toca las cuentas de prueba existentes. Corre aparte de `npm run test` (necesita `DATABASE_URL` real y red hacia Neon, que no existen en este entorno de Mac) — nuevo script `npm run test:integration`, a correr a mano en Windows, mismo criterio que `prisma generate`/`migrate`/`build`. Probado en Windows en dos rondas: la primera falló en `beforeAll` por latencia de Neon (la base "duerme" cuando está inactiva y el `maxWait` default de Prisma, 2 segundos, no alcanzaba para despertarla con dos conexiones simultáneas) — arreglado con más margen de tiempo y creación secuencial de los dos tenants. La segunda ronda **pasó las 10 pruebas de aislamiento** (las que importan: capa 1 y capa 2, incluido el caso "sin tenant fijado"), pero la limpieza (`afterAll`) reveló un hallazgo real, no relacionado con el aislamiento: `RespuestaCruda.responsable` (Usuario) no tiene `onDelete: Cascade` en el schema, a diferencia de sus otras dos relaciones — Postgres bloquea el borrado de un Usuario con respuestas propias (RESTRICT/NO ACTION, el default). No afecta producción hoy (no existe ninguna función de "borrar usuario" en la app), pero es una brecha real a tener en cuenta antes de construir una. Arreglado sin tocar el schema (el test borra `RespuestaCruda` a mano antes de borrar el tenant). Tercera ronda en Windows: **10/10 pruebas pasaron, limpieza incluida, sin errores** — RNF1 queda validado de punta a punta.

**RNF9 (instrumentación mínima): implementado y validado en Windows.** Al revisar qué faltaba antes de empezar el Incremento 2, se detectó que RNF9 nunca se había construido a pesar de ser parte explícita del criterio de "listo" del Incremento 1 (ADR-0002, junto con RF1-RF10 y RNF1) — esta sección del README había declarado el Incremento 1 "cerrado" antes de tiempo; queda corregido acá. RNF9 pide, sin ser "un sistema de analítica de producto completo", dos señales mínimas: (a) tiempo real de completar el cuestionario, contra el objetivo de 5 minutos de RNF2, y (b) cuántas recomendaciones de RF8 se marcaron como ejecutadas. Se agregaron dos tablas nuevas, mínimas (`MetricaCuestionario`, `RecomendacionEjecutada`), sin `empresaId` propio — mismo patrón que `RespuestaCruda`/`ResultadoConexion`/`ResultadoCiclo`: `set_config` manual + RLS por subconsulta a `CicloPulso` (`prisma/rls.sql` actualizado con las dos políticas nuevas). La duración se mide en el cliente (`ResponderCuestionarioForm.tsx` guarda el instante de montaje y calcula los segundos al enviar, sin un segundo viaje al servidor solo para marcar el inicio) y se persiste junto con las respuestas si el envío es válido (`registrarRespuestas.ts`, campo opcional — nunca bloquea el envío del cuestionario si falta). Un administrador puede marcar una recomendación como ejecutada desde `/dashboard/ciclos/[id]` (botón nuevo junto a cada recomendación, idempotente vía upsert) y ve el resumen agregado en una página nueva, `/dashboard/metricas` (solo administrador, sin filtros ni series temporales, tal como pide el requisito). De paso, aprovechando que ésta es la primera migración de schema real de todo este segmento (el resto de RF1-RF10/RNF1 se había diseñado deliberadamente para no necesitar ninguna, por la limitación de red del Mac), se agregó `onDelete: Cascade` a `RespuestaCruda.responsable` — el gap de FK real que había encontrado RNF1 al limpiar sus tenants de prueba. `tsc`/`eslint`/`vitest` limpios (**45/45 tests**, 4 nuevos para la función pura de cálculo de métricas).

**Bug real de entorno encontrado al migrar (Neon + shadow database):** `npx prisma migrate dev` fallaba con `P3014` ("permission denied to create database") porque ningún rol de Neon tiene `CREATEDB` — Prisma necesita una base de sombra temporal para diffear el schema y no puede crearla sola. Corregido agregando `shadowDatabaseUrl` al datasource de `prisma/schema.prisma`, apuntando a una segunda base (`chainpulse_shadow`) creada a mano desde la consola de Neon (eso no pasa por SQL, no necesita `CREATEDB`) — documentado en `.env.example` (`SHADOW_DATABASE_URL`).

**Incidente real al reconstruir `.env` en Windows (sin relación con el código):** al editar `.env` a mano para la migración, una edición en Notepad borró por error casi todo el archivo salvo `DATABASE_URL` y `RATE_LIMIT_STORE_URL` — se perdieron `NEXTAUTH_SECRET`, `SEED_DATABASE_URL`, `RESEND_API_KEY`, etc. Se reconstruyó rotando las contraseñas de `neondb_owner` y `chainpulse_app` en Neon y regenerando `NEXTAUTH_SECRET`; `RESEND_API_KEY`/`RESEND_FROM_EMAIL` quedaron vacíos (RF4 y el aviso de apertura de ciclo no van a poder enviar correo hasta cargarlos de nuevo desde el dashboard de Resend — no bloquea nada más, ver `abrirCiclo.ts`, que ya tolera fallos de envío). Detalle completo y credenciales pendientes de rotar otra vez (quedaron expuestas en el chat durante el diagnóstico) en [`SEGURIDAD-credenciales.md`](./SEGURIDAD-credenciales.md).

Probado en Windows de punta a punta con datos reales: se marcó como ejecutada la recomendación de un ciclo ya cerrado (botón "Marcar como ejecutada" → cambia a "Ejecutada el [fecha]"), `/dashboard/metricas` mostró correctamente "1 / 2 marcadas como ejecutadas"; luego se abrió un ciclo nuevo, se respondió el cuestionario como responsable y se cerró como administrador — `/dashboard/metricas` pasó a mostrar "Promedio: 0 min (8 s) sobre 2 respuestas. Dentro del objetivo de 5 minutos (RNF2): 2 / 2 (100%)" y "1 / 3 marcadas como ejecutadas" — coherente con los datos cargados. Con esto, el Incremento 1 completo (RF1-RF10, RNF1, RNF9) queda cerrado de verdad.

**Seguridad de credenciales:** ver [`SEGURIDAD-credenciales.md`](./SEGURIDAD-credenciales.md) — checklist de contraseñas/tokens que se compartieron durante la configuración del entorno y quedan pendientes de rotar.
